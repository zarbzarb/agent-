# 四、各题答案

## 一、文本生成与分词流程

### 第 1 题

**（1）补全代码**

```python
input_ids = tokenizer(prompt, return_tensors="pt").input_ids.to("cuda")
generation_output = model.generate(
    input_ids=input_ids,
    max_new_tokens=20,          # ← 生成 20 个新词元
)
print(tokenizer.decode(generation_output[0]))
```

**（2）输出开头的 `<s>` 是什么？是否需要手动输入？**

`<s>` 是 **BOS（Beginning Of Sequence，序列起始）特殊词元**。

- **不需要手动输入**。分词器在编码时会自动把它插到序列最前面。
- 作用：告诉模型"一个新的序列从这里开始"，同时保证推理时的输入格式与预训练时一致；
  多轮对话/多段拼接时它还充当"分隔与重启"的锚点。
- DeepSeek 同为 Llama 风格分词器，序列开头也是 `<s>`（本作业实际用的
  `deepseek-coder-1.3b-instruct` 把它写作 `<｜begin▁of▁sentence｜>`），道理完全一样。

**（补充）小模型拒答怎么办？**

本作业默认的 DeepSeek 只有 1.3B，而且 `deepseek-coder` 是**代码专用**模型，
直接问"写道歉邮件"它会给一句 "I'm sorry, but as an AI…"。
这不是分词/BOS 机制的问题，而是模型容量与训练目标的限制，**不影响本题要观察的分词流程**。
想看一封真正像样的道歉邮件，两条路：

1. 把 `from_pretrained("models/deepseek-coder-1.3b-instruct")` 换成更大、
   能力更强的 `deepseek-ai/deepseek-llm-7b-chat`（需 16GB+ 显存）；
2. 用**助手回复预填（assistant prefill）**：把助手的开头替它写好，让它从"已经答应了"
   的状态往下续写 —— 在 `q01_text_generation.py` 里给 `prompt` 后面加一句即可：

   ```python
   prompt += "Dear Sarah,"          # 只需这一行
   ```

   实测只多预填了这几个字符，同一个模型就从"拒答"变成写出一封完整的道歉邮件：
   `Dear Sarah, I hope this message finds you well. I am writing to express my deepest
   regret and apologies for the unfortunate situation…`
   这也是 OpenAI / Anthropic 都支持的用法，本质与作业里"prompt 末尾先加
   `<|assistant|>` 标记"是同一件事。

### 第 2 题

**（1）input_ids 的类型？`device='cuda:0'` 说明什么？**

- 类型是 **`torch.Tensor`**（`dtype=torch.int64` 的**二维**张量），形状 `[1, 25]`：
  第 1 维 `1` 是 **batch size**（批次大小，即 1 个句子），
  第 2 维 `25` 是 **sequence length**（序列长度，即 25 个词元）。
- `device='cuda:0'` 说明这个张量被放在**第 0 号 GPU 的显存**里。
  PyTorch 要求张量与模型同设备才能运算，所以分词后要 `.to("cuda")`；没有 GPU 时会是 `cpu`。

**（2）张量里的数字代表什么？**

每个数字是**词元 ID（token id）**，即该词元在分词器**词表中的下标**。
分词器内部维护一张"字符串 ↔ 整数"映射表（`"Write"→14350`、`"an"→385`…）。
模型不认识文字，只认识这些整数：输入时用整数查嵌入表取出向量，输出时再 `decode` 回文字。

### 第 3 题

**（1）为什么第一个词元是 `<s>`？**

因为分词器在编码时会**自动**在序列最前面插入 BOS 词元 `<s>`：
统一标识序列起点、与训练语料格式保持一致、便于多段文本的拼接与切分。

**（2）`apolog`、`izing`、`trag`、`ic` 说明了什么？**

说明该分词器采用**子词（subword）分词**（BPE / SentencePiece），而不是按整词或按字符切分：
罕见的整词会被拆成若干个**更常见、更小的子词片段**。

好处：

1. **彻底消除 OOV**：任何字符串都能由子词拼出来，不必退化成 `[UNK]`；
2. **词表规模可控**：Phi-3 只用了 32064 个词元就覆盖多语言，
   比词级分词（动辄百万词表）小得多，又比字符级分词序列短得多；
3. **复用词根词缀**：`apolog-` / `-izing` / `-ic` 被反复使用，
   形态相近的词（apologize / apologizing / apology）共享向量，彼此"借力"、
   对未见过的词形也能泛化；
4. 英文平均一词 1~3 个子词，序列不会过长，注意力计算量 O(n²) 也不至于爆炸。

### 第 4 题（填空）

| 特殊词元 | 用途 |
|---|---|
| **unk（未知）** | 未知词元 `[UNK]`。当分词器**没有为某类字符/词语进行特定编码**（词表里查不到、又无法拆成已知子词）时使用，用来占位表示"不认识的内容"。 |
| **sep（分隔符）** | 分隔符词元 `[SEP]`。用于需要为模型提供**两段文本**的特定任务（句对分类、问答、句子相似度重排序等）——在这类场景下模型被称为**交叉编码器 cross-encoder**——把两段文本分隔开。 |
| **pad（填充）** | 填充词元 `[PAD]`。用于填充模型输入中**未使用的位置**，因为模型通常要求输入数据具有**固定的长度**（也就是它的上下文窗口）；一个 batch 内短句要补齐到最长句的长度，配合 `attention_mask` 让模型忽略这些位置。 |
| **cls（分类）** | 分类词元 `[CLS]`。主要用于**分类任务**的特殊词元，放在句首，其最后一层的向量被当作整句的聚合表示，接一个分类头即可输出类别。 |
| **mask（掩码）** | 掩码词元 `[MASK]`。在（预）训练过程中用于**隐藏词元**，让模型根据上下文预测被遮住的词（如 BERT 的 MLM 任务），从而学到双向语义表示；推理时不使用。 |

> 补充：DeepSeek 使用 Llama 风格分词器，不用 BERT 这套 `[CLS]/[SEP]/[MASK]`，
> 而是用 `<s>`、`</s>`、`<｜end▁of▁sentence｜>`、`<｜Assistant｜>` 等控制标记；
> 但"需要一个专门词元承担某个功能"的设计思想是通用的。

### 第 5 题：测试文本中的"困难情况"（列举 6 种）

1. **大小写** —— `English and CAPITALIZATION`
   同一单词的大小写变体在词表中是**不同**词元。全都单独占位会撑大词表、割裂同一语义；
   统一转小写又会丢失"大写 = 专有名词/强调"的线索（Apple vs apple）。
   分词器必须在"压缩词表"和"保留大小写信息"之间取舍。

2. **英语以外的语言** —— `🕊鸟`（汉字）
   主流 BPE 词表以英文语料为主，对中日韩等**表意文字**覆盖很差。一个汉字常常找不到
   对应整字词元，只能回退成 UTF-8 字节片段，一个字被切成 2~4 个词元，
   序列拉长、语义碎片化，模型要"拼字节"才能还原一个字。

3. **表情符号 emoji** —— `🕊`
   emoji 在 UTF-8 下是 4 个字节，字节级分词器会把它拆成 4 个无语义片段；
   且 emoji 表每年还在新增，训练语料里出现极少，模型几乎学不到稳定语义。

4. **编程代码** —— `show_tokens False None elif == >= else:`
   ① 标识符常用下划线/驼峰粘连、没有空格分隔，边界难判断；
   ② 复合运算符（`==`、`>=`）是不可分割的语法单元，被切成 `=`+`=` 就破坏语义；
   ③ 关键字（`elif`、`None`、`False`）语义关键但形态极短，切错代价大；
   ④ 代码的字符分布与自然语言差别极大，通用语料的统计规律不适用。

5. **空白字符与缩进** —— `two tabs:"\t\t"` `Three tabs:"\t\t\t"`
   Python 靠**缩进**表达语法结构，"两个 tab"和"三个 tab"是完全不同的程序结构。
   但分词时连续空白常被归一化/合并，缩进层级信息就被抹掉；制表符与空格混用还会造成切分不一致。

6. **数字** —— `12.0*50=600`
   数字的切分策略直接决定模型的算术能力：随机按字节切会让模型难以对齐个位/十位；
   退化成一位一词元（`1`、`2`、`.`、`0`）更利于按位运算，但序列会变长。
   另外小数点、乘号、等号既像数字又像符号，边界模糊。

## 三、词元嵌入

### 第 6 题

**（1）`torch.Size([1, 4, 384])` 三个维度的含义**

| 维度 | 数值 | 含义 |
|---|---|---|
| 第 1 维 | **1** | **batch size（批次大小）**，本次只送了 1 个句子；设这一维是为了能一次并行处理多句、充分利用 GPU |
| 第 2 维 | **4** | **sequence length（序列长度 / 词元数）**，这句话共 4 个词元。注意是"词元数"而不是"单词数" |
| 第 3 维 | **384** | **hidden size / embedding size（隐藏维度）**，每个词元被表示成一个 384 维稠密向量（DeBERTa-v3-xsmall 的宽度就是 384） |

一句话：**1 个批次 × 4 个词元 × 每个词元 384 维向量**。

**（2）句子只有两个单词，为什么词元数是 4？**

因为 DeBERTa 的分词器会自动在句子首尾加上两个特殊词元：

```
[CLS]  Hello  world  [SEP]
```

- `[CLS]`：放在最前面，分类任务用，其最终向量被当作整句的聚合表示；
- `[SEP]`：放在最后面，句子结束/分隔标记（输入两段文本时也用它隔开）。

所以 **2 个实词 + 2 个特殊词元 = 4 个词元**，输出的序列长度是 4 而不是 2。

## 四、句子与文本嵌入

### 第 7 题

**（1）`vector.shape == (768,)` 表示什么？**

一个**一维**张量、长度 **768**，表示 **"Best movie ever!" 整句话被编码成了一个 768 维的稠密向量**。

与第 6 题对比即可看出关键差别：词元嵌入是"每个词元一个向量"（三维），
句子嵌入是"整句一个向量"（一维）。`shape` 里没有 batch 维是因为传入了单个字符串；
传列表就会得到 `(N, 768)`。有了这个定长向量，就能用余弦相似度直接比较句子语义、
或建向量索引做检索。

**（2）词元嵌入 vs 句子嵌入**

| | 词元嵌入 Token Embedding | 句子嵌入 Sentence / Text Embedding |
|---|---|---|
| 粒度 | 每个词元一个向量 | 整句 / 整段一个向量 |
| 形状 | `(batch, seq_len, hidden)` 三维 | `(hidden,)` 或 `(batch, hidden)` |
| 语义单位 | 单个词元及其上下文 | 整句整体语义 |
| 产生方式 | 模型 embedding 层输出 / 各层隐状态 | 句向量模型 + 池化（mean / max / CLS） |
| 长度 | 随句子长短变化 | 定长，与句子长短无关 |

联系：句子嵌入通常就是把词元嵌入**聚合**得到（如 mean-pooling 或取 `[CLS]` 向量）。

适合的任务：

- **词元嵌入** → 需要逐词输出或词级对齐的任务：序列标注（NER、词性标注、分词）、
  掩码语言建模、抽取式问答的答案定位，以及作为下游模型的输入特征。
- **句子嵌入** → 把整段文本当整体比较/检索/聚类的任务：语义检索与向量数据库召回（RAG）、
  语义相似度、去重、文本聚类、句级分类、推荐、跨语言对齐。

一句话记忆：**要"看词"用词元嵌入，要"比句子"用句子嵌入。**

## 五、预训练词嵌入（Word2vec、GloVe）

### 第 8 题

**（1）`(queen, 0.7839...)` 两个元素的含义**

- `'queen'` —— 与查询词 `king` 最**相似**的那个**词**；
- `0.7839...` —— 两者之间的**余弦相似度（cosine similarity）**，
  衡量两个向量方向的接近程度，取值范围约 `[-1, 1]`：越接近 1 越相似，接近 0 表示无关，为负表示语义相反。

列表第一项是 `('king', 1.0000001)`，因为查询词与自己相似度为 1
（不完全等于 1 是浮点误差；也说明 `most_similar` 会把查询词自己算进去）。

**（2）为什么 queen、prince、emperor 会与 king 相似？体现了什么性质？**

GloVe 在**维基百科级别的超大规模语料**上训练，核心是用"词共现统计"学习向量：
如果两个词总出现在相似上下文里（king、queen 周围总跟着 crown / throne / royal / palace），
它们的向量就会被拉近。king / prince / queen / emperor / ruler / kingdom / throne
共享"**君主、王室、统治、权力**"这一整套上下文，所以聚成一簇；
son / uncle / brother 则因为同属"亲属、血缘、继承"语境被拉了过来。

这体现了词嵌入的两个核心性质：

1. **分布式假设（Distributional Hypothesis）/ 语义相似性**：
   一个词的意义由它出现的上下文决定 → 上下文相似的词向量也相似；
2. **向量的线性可加性**：`king − man + woman ≈ queen`，
   说明"性别""王室"等语义被编码成向量空间里稳定的**方向**，
   因此可以做类比推理。

## 六、实战：使用 Word2vec 做歌曲推荐

### 第 9 题

**（1）"单词"和"句子"分别对应什么？**

这是经典的 **item2vec** 思路——把"物品序列"当成"句子"：

| 自然语言 | 本任务 |
|---|---|
| 单词 word | **一首歌 song_id** |
| 句子 sentence | **一条播放列表 playlist** |
| 语料 corpus | 全部用户的播放列表集合 |

于是"经常出现在同一歌单里的歌"等价于"经常出现在同一句话里的词"，向量会被拉近，
得到"相似歌曲"。整个过程是纯共现统计的**协同过滤**，无需任何人工标注。

（注意：歌单内歌曲没有严格顺序，"上下文"实际是"集合内共现"，这也是 `window` 要设大的原因。）

**（2）参数含义**

| 参数 | 含义 |
|---|---|
| `vector_size=32` | 每个歌曲向量的维度是 **32**。维度越高信息容量越大，但更易过拟合、训练更慢；本数据集共现信号相对简单，32 维性价比高。 |
| `window=20` | 上下文窗口**半径 20**，即预测某首歌时把它在歌单中前后各 20 首都当作上下文。歌单无序，窗口开大 ≈ 覆盖整条歌单，让同歌单内任意两首都能成为正样本对。 |
| `negative=50` | **负采样**抽 50 个不相关的歌作负例，替代昂贵的全词表 softmax。负例越多梯度估计越准、区分度越强，但每步更慢。 |
| `min_count=1`（附带） | 出现 ≥1 次的歌都保留。音乐数据长尾严重，默认的 5 会丢掉大量冷门歌。 |
| `workers=4`（附带） | 4 线程并行训练，模型异步更新，接近线性加速。 |

### 第 10 题：为什么这个模型能做出合理的歌曲推荐？

推荐结果（Billie Jean，ID=3822）本机实测为：
**Let The Music Play（Shannon，0.9905）、Kiss（Prince，0.9901）、
Wanna Be Startin' Somethin'（Michael Jackson，0.9890）、
P.Y.T. (Pretty Young Thing)（Michael Jackson，0.9883）、
I Wanna Dance With Somebody（Whitney Houston，0.9876）**
—— 清一色的 80 年代 funk / dance-pop，其中两首是 Michael Jackson 本人。

Holiday、Don't Stop 'Til You Get Enough）与此高度重合，风格完全一致。
这个结果非常合理，原因有四层：

1. **共现即相关**：训练语料是**真实用户的播放列表**。同一用户把 Michael Jackson、Prince、
   Madonna 放进同一个歌单，就说明它们"同类"。Skip-gram 把经常同歌单出现的歌曲向量互相拉近，
   等价于在做**协同过滤**——"喜欢 A 的人也喜欢 B" ⟹ B 就是推荐。
2. **无监督学到隐含属性**：训练时只喂了 `song_id`，没有任何流派/年代/BPM 标签；
   但"哪些歌经常一起出现"这一统计规律背后编码了**流派（funk-pop / dance-pop）、
   年代（80 年代）、歌手、受众**等信息，所以向量空间自动形成"MJ 舞曲区""摇滚区""古典区"等簇，
   推荐结果在风格上高度一致。
3. **相似度分数佐证簇内紧密**：与 2172（Fade To Black / Metallica）最相似的 5 首本机实测为
   **Unchained（Van Halen，0.9980）、Breaking The Law（Judas Priest，0.9974）、
   Run To The Hills（Iron Maiden，0.9971）、Blackout（Scorpions，0.9958）、
   The Last In Line（Dio，0.9958）** —— 清一色的重金属 / 硬摇滚，
   相似度几乎都在 0.995 以上，几乎是同一簇的近邻，说明歌手/风格维度被清晰地编码进了向量空间。
   （注：Word2vec 训练带随机性，每次重训推荐的歌曲会有小幅变化，但风格圈始终稳定。）
4. **简单、高效、可扩展**：不需要音频特征与人工标签，只要能拿到"用户歌单"这种隐式反馈，
   就能给任意歌曲算出邻居；配合 FAISS / HNSW 可支持上亿曲库的毫秒级召回——
   这正是工业界 item2vec / 双塔召回方案的思想源头。

## 七、查看 LLM 内部：模型结构与 KV 缓存

### 第 11 题

**（1）`Embedding(32064, 3072)` 两个数字的含义**

| 数值 | 含义 |
|---|---|
| **32064** | **词表大小 vocab_size** —— 模型一共认识 32064 个词元，**每一个词元占一行** |
| **3072** | **嵌入维度 hidden size（d_model）** —— 每个词元被映射成的稠密向量的长度 |

即一张 **32064 行 × 3072 列**的查找表：输入 token id（0~32063 的整数），
取出该 id 对应那一行的 3072 维向量，作为后续所有层的输入表示。
（`Embedding` 本身只有两个维度；真正送进模型时张量形状才变成 `[batch, seq_len, 3072]`。）

附加：`padding_idx=32000` 表示 id 32000 是 `<pad>` 填充词元，其嵌入**不参与梯度更新**
（永远是初始值），因为填充位不是真实内容。

**（2）堆叠了多少个 Phi3DecoderLayer？**

**32 层**。证据是 `(layers): ModuleList((0-31): 32 x Phi3DecoderLayer(...))`——下标 0~31。

每层包含两个子层：

- **注意力子层** `Phi3Attention`：`qkv_proj` 把 3072 维输入一次映射成 3×3072 = **9216** 维
  （Q、K、V 拼在一起），经旋转位置编码与因果注意力后由 `o_proj` 映射回 3072 维；
- **前馈子层** `Phi3MLP`（SwiGLU）：`gate_up_proj` 把 3072 维扩到 2×8192 = **16384** 维，
  分 gate/up 两支，经 SiLU 门控相乘后降到 8192 维，再由 `down_proj` 回到 3072 维。

每个子层前后有 RMSNorm 归一化与残差连接（Dropout 概率 0.0，推理时不生效）。
层数越多，模型的表达与"推理深度"越强，代价是参数更多、推理更慢。

**（3）为什么 lm_head 的输出维度恰好是 32064？它有什么用途？**

因为语言模型的最终任务是**预测下一个词元**：

1. 经过 32 层 Transformer 与最后的 norm，序列每个位置都有一个 3072 维向量；
2. `lm_head` 是一个 `3072 → 32064` 的线性层，把它映射成 **32064 个分数（logits）**，
   第 i 个分数表示"下一个词元是词表里第 i 个 token"的倾向；
3. 经 softmax 得到**整个词表上的概率分布**，再按贪心（argmax）或采样（top-k / top-p /
   temperature）挑出一个 token；
4. 把新 token 接到输入末尾喂回模型，循环往复，就得到整段**自回归生成**。

所以输出维度**必须等于词表大小**——词表里有多少候选 token，就至少要输出多少个分数。
同时会发现 `lm_head` 与 `embed_tokens` 的形状互为转置（32064×3072 vs 3072×32064），
因此很多模型会**共享权重**（weight tying），既省显存又能提升小模型效果。

> **换成 DeepSeek 后（本机实测）**：默认模型 `deepseek-ai/deepseek-coder-1.3b-instruct`
> 是 `LlamaForCausalLM` 结构 —— `embed_tokens: Embedding(32256, 2048)`、
> **24 个** `LlamaDecoderLayer`、`lm_head: Linear(2048, 32256)`，
> 词表 32,256 / 隐藏维度 2,048 / 16 个注意力头（head_dim=128）/ 中间层 5,504 / 上下文 16,384，
> 实测参数 1,346,471,936（13.46 亿）。若换成 7B 版（`deepseek-llm-7b-chat`）则是
> `Embedding(100015, 4096)`、30 层、`lm_head: Linear(4096, 100015)`。
> 三问的形式与答案完全一致：**行数 = 词表大小，列数 = 嵌入维度，lm_head 输出维度 = 词表大小**。
> 实测把 3 个词元送进去：`(1,3)` → embedding 后 `(1,3,2048)` → lm_head 后 `(1,3,32256)`，
> 每个位置都给出"下一个词元是词表里哪个 token"的完整分数分布。

### 第 12 题

**（1）KV 缓存为什么能大幅加速生成？**

自回归生成是**逐词元**进行的，每吐一个新词元就要再跑一次前向。而自注意力中每个位置都要做：

```
Attention(Q, K, V) = softmax(Q Kᵀ / √d) V
```

即"用当前词元的 Q 去和**之前所有词元**的 K 做点积得到权重，再用权重对**之前所有词元**的 V 加权求和"。

- **不使用缓存**：为了得到第 t 步的 K、V，必须把前面 t−1 个词元的 K、V **重新算一遍**，
  第 t 步计算量正比于 t；生成 n 个词元的总量 ≈ 1+2+…+n = **O(n²)**，绝大部分是重复劳动。
- **使用缓存**：注意 **第 i 个词元的 K、V 只依赖第 1..i 个词元**，
  与后面新生成的词元无关（因果注意力看不到未来），一旦算出就是**常量**，可以存起来反复复用。
  于是每步只需为新增的**那一个**词元计算 K、V 并**追加**到缓存，再让它与缓存中全部 K、V 做注意力。
  单步从 O(t) 降到 **O(1)**，整体从 **O(n²) 降到 O(n)**。

这就是 100 个词元能从 **O(n²) 降到 O(n)** 的原因。作业给出的参考值是
**21.8 秒 → 4.5 秒（约 4.8×）**；本机用 DeepSeek-1.3B + RTX 2060 实测（prompt 26 词元、
生成 100 词元）为 **14.01 秒 → 893.64 秒（约 63.8×）**。
具体倍数随模型、显卡、prompt 长度与实现不同而变化，但结论一致：**序列越长、生成越多，
禁用缓存的重复计算越夸张，差距越大**。

**代价**：KV 缓存占用显存 ≈ `2 × 层数 × 序列长度 × 隐藏维度 × 字节数`，
随序列长度**线性增长**。所以长上下文很吃显存，工程上才有了 MQA / GQA（共享 K、V 头）、
PagedAttention（显存分页）、缓存量化等优化。

**推论**：生成分为两个阶段——

- **Prefill（预填充）**：把整个 prompt 一次性并行编码，算好并写入全部 K、V 缓存；
  大矩阵乘法，**计算密集**，GPU 利用率高。
- **Decode（解码）**：逐词元生成，每步只算 1 个词元的 Q/K/V，瓶颈在**读缓存**，
  属**访存密集**，GPU 算力大量空闲。

这也正是 **LLM API 普遍采用流式输出**的原因：让用户先看到前几个词，而不是干等整段生成完。

**（2）为什么生成第二个词元时只需计算新词元的缓存？**

因为**因果（causal）注意力**保证"过去不受未来影响"：第 i 个位置的 K、V 在每一层都只由
第 1..i 个词元决定，一旦算完就固定不变。具体到这一步：

- 第一步处理 prompt 时（prefill），模型已经把 prompt 里**所有**词元的 K、V 在每一层算好并存入缓存；
- 生成第二个词元时，真正"新"的只有上一步刚生成的那一个词元，它需要（在每一层）计算自己的
  Q、K、V；而 prompt 部分的 K、V **直接从缓存读取**，无需重算；
- 于是这一步的计算量只与"新增的 1 个词元"有关，与 prompt 有多长**无关**；
  prompt 越长，省下的重复计算越多，加速越明显。

公式角度：

```
o_t = Σ_{i≤t} softmax(q_t · k_iᵀ / √d) · v_i
```

其中 `{k_i, v_i}_{i<t}` 全部来自缓存，本步只新算 `q_t, k_t, v_t`。

这也是"缓存"名字的由来：缓存的是每层的 **K**ey 和 **V**alue；
Q 不需要缓存，因为每个位置的 Q 只用一次，用完即丢。

### 第 13 题 —— 交付物：`q13_practice.py`

**（1）it 被切分成了几个词元？**

**1 个**。`it` 是高频英文单词，完整存在于 DeepSeek 分词器词表中，
只对应**唯一一个** token id，不会被拆成 `i` + `t` 或其它子词。

对比：罕见词才会被拆开（`antidisestablishmentarianism` → 多个子词），
越常见的词越"完整"。

**（2）为什么代词 it 的预测需要依赖前文（注意力机制的作用）？**

代词**本身没有独立语义**——`it` 到底指谁完全由上下文决定。本句
`The dog chased the squirrel because it` 中，`it` 既可以指 the dog 也可以指 the squirrel，
只有读了前文才可能判断。这正是**自注意力机制**要解决的问题：

1. **上下文相关表示**：Transformer 里每个词元的向量不是固定词表向量，
   而是它与本句所有其他词元交互后的**加权聚合**。
   计算 `it` 时，它的 Q 与前面所有词元（the / dog / chased / the / squirrel / because）的 K 做点积
   得到注意力权重 α，再用 α 对它们的 V 加权求和——于是 `it` 的表示里"混入"了
   dog 和 squirrel 的信息，而不是孤立的"它"。
2. **因果遮罩（causal mask）**：自回归模型只允许看到自己及**之前**的词元，
   未来位置被 mask 成 −∞。"依赖前文"是机制上的**硬约束**。
3. **多层堆叠 → 逐步消歧**：浅层注意力捕捉语法搭配（it 与 chased / because 的关系），
   深层才完成**指代消解**（判断 it 更可能是 squirrel，因为松鼠会爬树逃走，狗在追）；
   本机 24 层（Phi-3 为 32 层）逐层精炼，`lm_head` 最终才输出 `climbed / ran / escaped`
   这类符合松鼠行为的词。
4. **反证**：把前文换成 `…because it was hungry.` 模型会偏向 the dog；
   换成 `…because it was scared.` 则偏向 the squirrel。
   **同一个词、同一位置，只因上下文不同，内部表示与预测结果就不同**——
   这就是"必须依赖前文"最直观的证据。

`q13_practice.py` 除了完成分词与打印词元 ID，
还会真实抽取一层的注意力矩阵，打印并可视化 `it` 对各前文词元的注意力权重分布
（输出 `q13_attention_heatmap.png`），用数据直接展示"它把目光放在了谁身上"。
